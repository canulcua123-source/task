Resumen de cambios

  • CRÍTICO cliente → vehiculo: CASCADE → RESTRICT
  • CRÍTICO vehiculo → orden_servicio: SET NULL → RESTRICT
  • CRÍTICO Tabla mecanico_orden creada (N:M mecánicos por orden)
  • DISEÑO nombre separado en nombre, apellido_paterno, apellido_materno en cliente y mecanico
  • DISEÑO costo_total eliminado — calcularlo con vista
  • DISEÑO Tablas especialidad + mecanico_especialidad creadas
  • DISEÑO estado debe usar ENUM o tabla catálogo
  • DISEÑO fecha_salida agregada a orden_servicio
  • MENOR kilometraje: BIGINT → INTEGER
  • MENOR placa: VARCHAR(7) → VARCHAR(15)
  • MENOR Índices en placa, folio, correo, codigo_p
  • MENOR detalle_orden: PK compuesta → id_detalle propio

Nuevas áreas de mejora detectadas

  • NUEVO Falta UNIQUE en placa — Dos vehículos no deben tener la misma placa. Sin constraint UNIQUE se pueden duplicar registros.
  • NUEVO Falta UNIQUE en correo de cliente — Permite registrar el mismo cliente dos veces con el mismo correo.
  • NUEVO Falta UNIQUE en codigo_p de refacción — El código de parte debe ser único por definición.
  • NUEVO Sin validación de cantidad > 0 — En detalle_orden nada impide cantidades negativas o cero. Agregar CHECK (cantidad > 0).
  • NUEVO Sin validación de precio >= 0 — En detalle_orden y refaccion falta CHECK (precio >= 0).
  • NUEVO Sin validación de existencias >= 0 — Puede quedar negativo sin un CHECK constraint.
  • NUEVO Sin historial de precios de refacción — Si el precio cambia, no hay registro del precio anterior. Considerar tabla historial_precio o confiar en que detalle_orden.precio es el snapshot.
  • NUEVO Falta created_at / updated_at — Ninguna tabla tiene timestamps de auditoría. Esencial para rastrear cuándo se creó o modificó un registro.

Consultas con INNER JOIN y LEFT JOIN

Usando el esquema corregido (con apellidos separados). Se demuestra por qué importa separar los apellidos.

1. Clientes con sus vehículos — INNER JOIN

Solo clientes que TIENEN vehículos. Demuestra filtro por apellido_paterno.

SELECT
    c.nombre,
    c.apellido_paterno,
    c.apellido_materno,
    v.placa,
    m.nombre AS modelo,
    f.nombre AS fabricante
FROM cliente c
INNER JOIN vehiculo v     ON v.id_cliente = c.id_cliente
INNER JOIN modelo m       ON v.id_modelo = m.id_modelo
INNER JOIN fabricante f   ON m.id_fabricante = f.id_fabricante
WHERE c.apellido_paterno = 'García'
ORDER BY c.apellido_paterno, c.apellido_materno, c.nombre;

¿Por qué INNER JOIN? Solo nos interesan clientes que tengan al menos un vehículo registrado.
¿Por qué separar apellidos? Permite WHERE apellido_paterno = 'García' — imposible si todo está en un solo campo nombre.

2. Clientes SIN vehículos — LEFT JOIN

Detecta clientes registrados que nunca han traído un vehículo.

SELECT
    c.apellido_paterno || ' ' || c.apellido_materno || ', ' || c.nombre AS nombre_completo,
    c.telefono,
    c.correo
FROM cliente c
LEFT JOIN vehiculo v ON v.id_cliente = c.id_cliente
WHERE v.id_vehiculo IS NULL;

¿Por qué LEFT JOIN? Necesitamos TODOS los clientes, incluso los que no tienen vehículo. El WHERE IS NULL filtra solo los huérfanos.
Apellidos: Concatenamos en formato "Apellido Apellido, Nombre" para reportes formales.

3. Órdenes con mecánicos asignados — INNER JOIN (tabla intermedia)

Muestra todos los mecánicos que trabajaron en cada orden.

SELECT
    os.folio,
    os.fecha_ingreso,
    m.nombre || ' ' || m.apellido_paterno AS mecanico,
    mo.rol,
    os.estado
FROM orden_servicio os
INNER JOIN mecanico_orden mo ON mo.id_orden = os.id_orden
INNER JOIN mecanico m        ON m.id_mecanico = mo.id_mecanico
ORDER BY os.fecha_ingreso DESC;

¿Por qué INNER JOIN? Solo órdenes que tienen mecánico asignado. La tabla mecanico_orden permite N mecánicos por orden.

4. Mecánicos SIN órdenes asignadas — LEFT JOIN

Detecta mecánicos ociosos (sin trabajo asignado).

SELECT
    m.nombre,
    m.apellido_paterno,
    m.apellido_materno
FROM mecanico m
LEFT JOIN mecanico_orden mo ON mo.id_mecanico = m.id_mecanico
WHERE mo.id_orden IS NULL;

¿Por qué LEFT JOIN? Queremos TODOS los mecánicos, y el IS NULL revela los que no tienen ninguna orden.

5. Detalle de orden con refacciones — INNER JOIN

Lista las refacciones usadas en una orden específica con subtotales.

SELECT
    r.codigo_p,
    r.nombre AS refaccion,
    d.cantidad,
    d.precio AS precio_unitario,
    (d.cantidad * d.precio) AS subtotal
FROM detalle_orden d
INNER JOIN refaccion r ON r.id_refaccion = d.id_refaccion
WHERE d.id_orden = 1;

¿Por qué INNER JOIN? Cada detalle DEBE tener una refacción (FK obligatoria). No puede haber detalle sin refacción.

6. Refacciones SIN uso — LEFT JOIN

Refacciones en inventario que nunca se han usado en ninguna orden.

SELECT
    r.codigo_p,
    r.nombre,
    r.existencias,
    r.precio
FROM refaccion r
LEFT JOIN detalle_orden d ON d.id_refaccion = r.id_refaccion
WHERE d.id_detalle IS NULL
ORDER BY r.existencias DESC;

¿Por qué LEFT JOIN? TODAS las refacciones, y el IS NULL filtra las que nunca aparecen en un detalle. Útil para limpiar inventario muerto.

7. Buscar duplicados por apellidos — INNER JOIN (self-join)

Encuentra clientes posiblemente duplicados comparando apellidos. IMPOSIBLE sin campos separados.

SELECT
    c1.id_cliente,
    c1.nombre || ' ' || c1.apellido_paterno || ' ' || c1.apellido_materno AS cliente_1,
    c2.id_cliente,
    c2.nombre || ' ' || c2.apellido_paterno || ' ' || c2.apellido_materno AS cliente_2
FROM cliente c1
INNER JOIN cliente c2
    ON  c1.apellido_paterno = c2.apellido_paterno
    AND c1.apellido_materno = c2.apellido_materno
    AND c1.id_cliente < c2.id_cliente;

¿Por qué INNER JOIN? Self-join: compara la tabla consigo misma. Solo muestra pares donde coinciden ambos apellidos.
¿Por qué separar apellidos? Con un solo campo nombre, habría que usar LIKE o SPLIT_PART — lento, frágil e impreciso.

8. Historial completo de un vehículo — INNER JOIN múltiple

Todo el historial de servicios de un vehículo con su dueño, modelo y fabricante.

SELECT
    v.placa,
    f.nombre AS fabricante,
    mo.nombre AS modelo,
    c.apellido_paterno || ' ' || c.nombre AS propietario,
    os.folio,
    os.fecha_ingreso,
    os.fecha_salida,
    os.diagnostico,
    os.estado
FROM vehiculo v
INNER JOIN cliente c         ON v.id_cliente = c.id_cliente
INNER JOIN modelo mo         ON v.id_modelo = mo.id_modelo
INNER JOIN fabricante f      ON mo.id_fabricante = f.id_fabricante
INNER JOIN orden_servicio os ON os.id_vehiculo = v.id_vehiculo
WHERE v.placa = 'ABC1234'
ORDER BY os.fecha_ingreso DESC;

¿Por qué INNER JOIN? Todas las relaciones son obligatorias: un vehículo DEBE tener cliente, modelo y fabricante.

9. Modelos SIN vehículos registrados — LEFT JOIN

Modelos en catálogo que ningún cliente ha registrado.

SELECT
    f.nombre AS fabricante,
    m.nombre AS modelo
FROM modelo m
INNER JOIN fabricante f ON m.id_fabricante = f.id_fabricante
LEFT JOIN vehiculo v   ON v.id_modelo = m.id_modelo
WHERE v.id_vehiculo IS NULL
ORDER BY f.nombre, m.nombre;

¿Por qué LEFT JOIN en vehiculo? Queremos TODOS los modelos, y el IS NULL filtra los que no tienen vehículos. El INNER con fabricante es porque todo modelo DEBE tener fabricante.

10. Reporte: total facturado por cliente — INNER JOIN + GROUP BY

Cuánto ha gastado cada cliente, ordenado por apellido. Demuestra por qué costo_total es innecesario.

SELECT
    c.apellido_paterno,
    c.apellido_materno,
    c.nombre,
    COUNT(DISTINCT os.id_orden) AS total_ordenes,
    SUM(d.cantidad * d.precio)  AS total_facturado
FROM cliente c
INNER JOIN vehiculo v         ON v.id_cliente = c.id_cliente
INNER JOIN orden_servicio os  ON os.id_vehiculo = v.id_vehiculo
INNER JOIN detalle_orden d    ON d.id_orden = os.id_orden
GROUP BY c.id_cliente, c.apellido_paterno, c.apellido_materno, c.nombre
ORDER BY c.apellido_paterno, c.apellido_materno;

¿Por qué INNER JOIN? Solo clientes con órdenes que tienen refacciones. Sin datos = sin factura.
¿Por qué no necesitas costo_total? El SUM(cantidad * precio) lo calcula al vuelo, siempre actualizado.
Apellidos: El ORDER BY apellido_paterno, apellido_materno da orden alfabético real — imposible con un campo nombre mezclado.

¿Cuándo usar cada JOIN?

  • INNER JOIN — Cuando ambas tablas DEBEN tener datos. Si no hay coincidencia, la fila NO aparece. Ideal para relaciones obligatorias (vehículo→modelo, detalle→refacción).
  • LEFT JOIN — Cuando quieres TODOS los registros de la tabla izquierda, aunque no tengan coincidencia en la derecha. Ideal para buscar "qué NO tiene relación" (clientes sin vehículos, refacciones sin uso, mecánicos ociosos).
  • Regla simple — ¿Buscas lo que SÍ existe en ambos lados? → INNER. ¿Buscas lo que FALTA en un lado? → LEFT + IS NULL.
